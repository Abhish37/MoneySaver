CONFIDENTIAL & PROPRIETARY

1. Executive Summary

Welcome to the official, comprehensive project documentation for MoneySaver (internally codenamed SaverStack). This document synthesizes the Product Requirements Document (PRD v1.1) and Technical Requirements Document (TRD v1.0) into a single source of truth for all stakeholders, engineering teams, and strategic partners. It covers every aspect of the platform's vision, technical implementation, risk vectors, and future roadmap.

1.1 Project Overview & Mission

Mission: To democratize extreme savings for the Indian consumer by algorithmically stacking disparate discounts into a single, seamless checkout experience.

Vision: To become the default layer between the consumer and e-commerce platforms, redirecting billions of rupees from corporate margins back into the pockets of the middle class.

MoneySaver is a cutting-edge web application designed primarily for Indian Gen Z and Millennial shoppers (aged 18-35). It acts as an intelligent aggregator and optimizer for e-commerce transactions on major platforms such as Amazon India, Flipkart, Myntra, and Zomato. Instead of requiring users to manually search for coupons, compare credit card offers, or navigate affiliate cashback portals, MoneySaver's 5-Layer Savings Stacker Engine performs complex deterministic calculations in real-time to present the absolute lowest Net Payable Amount.

1.2 The Indian E-commerce Savings Problem

The Indian e-commerce market is projected to reach $350 billion by 2030. However, the discount ecosystem is highly fragmented, intentionally opaque, and structurally hostile to the average consumer. Brands and marketplaces use multi-layered discount strategies—a combination of baseline prices, limited-time promo codes, bank-specific credit card discounts (often rotating weekly), and affiliate cashback networks—to price discriminate.

The average consumer leaves approximately 12-18% of potential savings on the table per transaction because:

  • Cognitive Overload: Checking CashKaro, then searching Telegram groups for coupons, then verifying which of their 4 credit cards gives the best discount on Flipkart on a Tuesday is exhausting.
  • Data Silos: Card offers are locked in bank PDFs or separate apps (like Cred); coupons are on site A; affiliate links are on site B.
  • Expiry Anxiety: Coupons and bank offers expire rapidly, leading to FOMO but also frequent disappointment at checkout.

1.3 MoneySaver's Unique Position

MoneySaver solves this by inverting the model. Instead of the user hunting for discounts, they input their cart details, and MoneySaver computes the optimal path to checkout. We are not just a "coupon site"; we are a deterministic financial calculation engine.

Our unique 5-Layer Savings Stacker Engine mathematically proves the best possible price by evaluating:

  1. Base Product Price
  2. Store Coupon / Promo Code (via scraping and OCR)
  3. Discounted Gift Voucher availability
  4. Bank Card / UPI Instant Discount logic
  5. Affiliate Cashback Percentage
Example Calculation: A user wants to buy headphones listed at ₹2,000. Base: ₹2,000 → Code "AUDIO15" (-₹300) → Pay with HDFC Millennia (-5% voucher = -₹85) → Instant 10% HDFC discount (-₹170) → CashKaro affiliate link (6% = -₹102). Final Net Payable: ₹1,343 (Saved ₹657 or 32.8%)

1.4 Business Model

MoneySaver operates on a zero-friction, free-to-use model for consumers, monetizing through B2B channels and performance marketing:

  • Phase 1 (Current): Affiliate Commissions. Every transaction routed through our Stacker Engine utilizes our affiliate links (e.g., EarnKaro, Cuelinks, INRDeals). We earn 2-12% commission on the Gross Merchandise Value (GMV). We pass a portion of this back as cashback to the user, keeping the delta as revenue.
  • Phase 1.5: Gift Card Arbitrage. By redirecting users to buy discounted gift cards (via affiliate links, zero-KYC on our end), we earn a flat commission per voucher sold.
  • Phase 2 (Roadmap): Premium Subscription. A ₹99/month "Saver Pro" tier that unlocks automated browser extension application of codes, premium credit card tracking, and zero-delay cashback withdrawals.

1.5 Competitive Differentiation

How we differ from existing players:

  • vs. Single Coupon Sites (Coupondunia, GrabOn): They only provide coupons. We provide the stack—coupons + cards + vouchers. We also crowdsource via OCR, ensuring fresher codes.
  • vs. Bank Apps (SmartBuy, YONO): Bank apps only show offers for their specific bank. We are bank-agnostic and allow users to select which cards they own to compute the best one.
  • vs. Cashback Apps (CashKaro): CashKaro requires you to click out from their app. MoneySaver integrates the cashback calculation directly into the upfront checkout decision process.

2. Product Deep Dive

This section details the seven core features of MoneySaver, user personas, and explicit scope boundaries.

2.1 Core Features

1. Screenshot Coupon Parser (OCR)

The Problem: The best coupons are often hidden in Instagram ads, YouTube sponsor reads, or physical flyers. Typing these out is friction.
The Solution: Users can upload a screenshot of any ad. We use Google Cloud Vision API to extract text, run RegEx to identify likely promo codes (e.g., words in ALL CAPS with numbers, next to words like "OFF" or "%"), and automatically inject them into our system.
Flow: User uploads image -> S3 ephemeral bucket -> Next.js Server Action -> GCP Vision API -> Text extraction -> RegEx parsing -> Code identified -> User validates -> Added to public database.

2. Community & System Coupon Vault

A decentralized, continuously updated repository of promo codes. It features a Reddit-style upvote/downvote system. To combat stale codes, we implement a 24-hour cron job that flags codes with a >30% downvote ratio for manual review or automatic deprecation (AMD-03).

3. Multi-Tier Savings Stacker Engine

The heart of the application. A deterministic algorithm that takes `SavingsStackInput` (cart value, store, user cards) and outputs `SavingsStackOutput`. It respects the order of operations (e.g., instant bank discounts apply to the cart value after the promo code is applied, but before cashback is calculated).

4. Cross-Platform Price Matrix

For standard electronic or FMCG goods, the Stacker Engine will soon query APIs to show the "Post-Stack Price" across Amazon, Flipkart, and Croma simultaneously, proving where the user gets the best final deal based on their specific wallet contents.

5. Payment & Card Optimizer

Users can (optionally, securely) select which credit/debit cards they hold (e.g., "SBI Cashback", "HDFC Millennia", "Amazon ICICI"). The Engine queries the `bank_offers` table to find the highest applicable instant discount or reward point yield for the specific store and cart value.

6. Discounted Voucher Integration (AMD-05)

Instead of acting as a marketplace and dealing with RBI KYC regulations for prepaid instruments, we act as an affiliate redirector for platforms like Gyftr or Woohoo. If a 5% discount voucher is available for Myntra, we factor it into the stack and provide the affiliate link to purchase it.

7. Product & Store Deal Search

A fast, cached search interface (powered by Upstash Redis) allowing users to search for "Zomato" or "Nike" and instantly see the current active stack matrix.

2.2 User Personas

Persona A: Rohan (22, College Student)
Profile: Tech-savvy, low disposable income, has one basic SBI debit card, heavily uses UPI.
Scenario: Ordering a pizza on Zomato. Rohan uses MoneySaver to find the best promo code (extracted via OCR from a Telegram group earlier that day). MoneySaver tells him his SBI debit card gives no discount, but buying a Zomato voucher via Amazon Pay UPI yields 5% cashback. He follows the stack and saves ₹120 on his ₹800 order.
Persona B: Ananya (29, Software Engineer)
Profile: High disposable income, holds 4 premium credit cards (HDFC Infinia, SBI Cashback, Axis Magnus). Optimizes for maximum reward points.
Scenario: Buying a ₹1,20,000 MacBook on Flipkart. Ananya inputs her cards into the Stacker Engine. The engine calculates that while HDFC offers an instant ₹5,000 discount, using her SBI Cashback card via a specific affiliate link actually yields ₹6,000 in statement credit. She chooses the optimal path.

2.3 Out of Scope (What we are NOT building)

To maintain technical focus and legal safety, the following are strictly out of scope for v1.x:

  • Direct Checkout: We do not process payments or host the final cart. We are an aggregator/comparator.
  • Account Scraping: We do not ask for users' bank login credentials or scrape their emails for receipts. Card selection is manual and generic (e.g., "I have an HDFC card", not "Here is my card number").
  • Guaranteed Cashback: Because affiliate networks can drop tracking cookies, we estimate cashback but clearly state it is subject to partner tracking.

4. Technical Architecture

The system is built on a modern, serverless stack optimizing for low latency (Stacker Engine ≤ 150ms), high developer velocity, and zero-maintenance infrastructure.

4.1 System Architecture Diagram

[CLIENT BROWSER] | | (HTTPS / Next.js App Router) v [VERCEL EDGE NETWORK] ---> [UPSTASH REDIS] | (Rate Limiting & Search Cache) | +---> (Server Components) ----> [CLERK AUTH] | +---> (Server Actions) | +---> [GCP VISION API] (OCR Service) | +---> [AWS S3] (Ephemeral Image Uploads) | +---> [NEON POSTGRESQL] (Drizzle ORM) - users - stores - coupons - bank_offers - voucher_deals

4.2 Frontend Architecture (Next.js 14+ App Router)

We leverage React Server Components (RSC) to ship zero JavaScript to the client for static pages (like the landing page and basic store listings). Interactive client components (like the Stacker UI, which requires Zustand for state management) are explicitly marked with "use client". Styling is handled via Tailwind CSS and shadcn/ui for accessible, unstyled radix primitives.

4.3 Backend Architecture (Server Actions)

Instead of traditional REST API routes, we use Next.js Server Actions for mutations (e.g., submitting a coupon, upvoting). This provides end-to-end type safety with TypeScript and integrates seamlessly with React's form transitions.

4.4 Pipeline A: OCR Screenshot Ingestion

  1. Client requests a pre-signed S3 URL from a Server Action.
  2. Client uploads the image directly to AWS S3 (bypassing Vercel's payload limits).
  3. Client calls `processOCRAction` with the S3 object key.
  4. Server fetches the image stream, sends to GCP Vision API.
  5. Server applies RegEx: /[A-Z0-9]{4,15}/g to find potential codes.
  6. Returns potential codes to client. S3 lifecycle policy deletes the image after 15 minutes.

4.5 Pipeline B: Savings Stacker Engine (The Algorithm)

The core algorithm is a pure TypeScript function executed on the edge or server.

// Interface Definitions
interface SavingsStackInput {
  basePrice: number;
  storeId: string;
  userId?: string;
  selectedCardIds?: string[];
}

interface SavingsStackOutput {
  basePrice: number;
  bestCoupon: { code: string; discountAmount: number; source: 'PUBLIC' | 'PERSONAL' };
  voucherOption?: { provider: string; purchaseCost: number; faceValue: number; netSavings: number };
  affiliateCashback: { network: string; cashbackAmount: number; percentage: number };
  bestCardOffer?: { bankName: string; cardName: string; discountAmount: number };
  finalNetPayable: number;
  totalSaved: number;
  effectiveDiscountPercentage: number;
}

Logic Flow: The engine queries the DB in parallel for all coupons, bank offers, and vouchers for the storeId. It then permutes the valid combinations. Note: Bank instant discounts are usually applied to the post-coupon cart value, while cashback is applied to the final paid amount (excluding tax/shipping if specified in JSONB conditions).

4.6 TRD Decisions Log (The "Why")

  • TRD-D01: Next.js App Router. Chosen for superior SEO (critical for "StoreName coupons" queries) and Server Components performance.
  • TRD-D02: Drizzle ORM over Prisma. Prisma's Rust engine is heavy and has cold start issues on serverless. Drizzle is lightweight SQL-like syntax and natively supports Neon's HTTP driver.
  • TRD-D03: Upstash Redis. Pay-per-request pricing fits our bursty traffic profile perfectly, unlike ElastiCache which requires provisioned instances.
  • TRD-D04: Neon PostgreSQL. Native branching allows every GitHub PR to get its own isolated database clone instantly.
  • TRD-D07: shadcn/ui. Copy-paste components mean we own the code, preventing future bloat from massive UI library dependencies.

5. Database Schema

We utilize a highly normalized, relational schema in PostgreSQL (hosted on Neon). We rely heavily on PostgreSQL's JSONB capabilities for flexible condition logic (e.g., "Valid only on electronics" or "Max discount ₹500").

5.1 Data Definition Language (DDL)

-- 1. USERS TABLE
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    clerk_id VARCHAR(255) UNIQUE NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    full_name VARCHAR(255),
    cumulative_savings NUMERIC(10, 2) DEFAULT 0.00,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. STORES TABLE
CREATE TABLE stores (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL,
    slug VARCHAR(255) UNIQUE NOT NULL,
    logo_url VARCHAR(1024),
    base_url VARCHAR(1024),
    affiliate_partner_name VARCHAR(100),
    affiliate_redirect_url VARCHAR(1024),
    default_cashback_percent NUMERIC(5, 2) DEFAULT 0.00
);

-- 3. COUPONS TABLE
CREATE TABLE coupons (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    store_id UUID REFERENCES stores(id) ON DELETE CASCADE,
    user_id UUID REFERENCES users(id) ON DELETE SET NULL, -- Null means system/scraped
    code VARCHAR(50) NOT NULL,
    discount_type VARCHAR(20) CHECK (discount_type IN ('PERCENTAGE', 'FLAT')),
    discount_value NUMERIC(10, 2) NOT NULL,
    min_cart_value NUMERIC(10, 2) DEFAULT 0.00,
    max_discount_amount NUMERIC(10, 2),
    source VARCHAR(50) CHECK (source IN ('PUBLIC_SCRAPED', 'USER_OCR', 'COMMUNITY')),
    is_active BOOLEAN DEFAULT TRUE,
    upvotes INTEGER DEFAULT 0,
    downvotes INTEGER DEFAULT 0,
    expires_at TIMESTAMP WITH TIME ZONE,
    conditions JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 4. BANK OFFERS TABLE
CREATE TABLE bank_offers (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    store_id UUID REFERENCES stores(id) ON DELETE CASCADE,
    bank_name VARCHAR(100) NOT NULL,
    card_type VARCHAR(100) NOT NULL,
    discount_percent NUMERIC(5, 2) NOT NULL,
    max_discount_amount NUMERIC(10, 2) NOT NULL,
    min_transaction_amount NUMERIC(10, 2) DEFAULT 0.00,
    is_active BOOLEAN DEFAULT TRUE,
    valid_until TIMESTAMP WITH TIME ZONE,
    conditions JSONB
);

-- 5. VOUCHER DEALS TABLE
CREATE TABLE voucher_deals (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    store_id UUID REFERENCES stores(id) ON DELETE CASCADE,
    provider_name VARCHAR(100) NOT NULL,
    discount_percent NUMERIC(5, 2) NOT NULL,
    affiliate_purchase_url VARCHAR(1024) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE
);

5.2 Indexing & Performance Strategy

To meet the ≤150ms Stacker Engine response time, critical read paths are indexed:

  • CREATE INDEX idx_coupons_store_active ON coupons(store_id) WHERE is_active = TRUE; (Partial index for extreme speed).
  • CREATE INDEX idx_bank_offers_store ON bank_offers(store_id, is_active, valid_until);
  • CREATE UNIQUE INDEX idx_users_clerk_id ON users(clerk_id);

JSONB Usage: The `conditions` column in `coupons` might look like: {"categories_excluded": ["electronics", "gold"], "new_user_only": false}. This allows unstructured business logic without migrating the schema constantly.

6. Authentication & Security

6.1 Auth Flow (Clerk)

We outsource identity management to Clerk to ensure enterprise-grade security and zero maintenance of password hashes. Users authenticate via Google OAuth or Email OTP. Upon successful authentication, Clerk issues a JWT session token. Our middleware intercepts requests, verifies the Clerk JWT, and attaches the userId. A Clerk webhook (user.created) syncs the user profile into our Neon users table.

6.2 OWASP Top 10 Mitigations

  • Injection: Drizzle ORM automatically parameterizes all SQL queries, eliminating SQL injection vectors.
  • XSS: Next.js automatically escapes all React rendered content. We implement a strict Content Security Policy (CSP) header.
  • CSRF: Handled by Clerk's session management (SameSite cookies).
  • Broken Access Control: Server Actions explicitly check `auth().userId` before allowing mutations (like uploading a coupon). Users can only delete coupons they created.
  • Rate Limiting: Implemented via Upstash Redis.
    • Public Stacker Search: 30 req/min/IP
    • OCR Upload: 5 req/min/User (prevents cloud bill spikes)
    • Sign-up/OTP: 3 req/hour/IP (bot protection)

6.3 Data Privacy & Ephemerality

We practice data minimization. We do not store PAN cards, credit card numbers, or passwords. OCR images uploaded by users are stored in an AWS S3 bucket with a strict lifecycle policy that permanently deletes objects 15 minutes after upload. This ensures that if a user accidentally uploads a screenshot containing personal messages, it is destroyed almost immediately after the API processes it.

6.4 Affiliate Redirect Security (HMAC)

To prevent malicious actors from scraping our affiliate links and replacing our affiliate tags with theirs, our redirect endpoints generate short-lived, HMAC-signed URLs. Example: /api/redirect?store=zomato&sig=a9f8b7c6. The signature is validated server-side before issuing the 302 redirect to the affiliate network.

7. Storage Strategy

We utilize a specialized, multi-tiered approach to storage to balance cost, performance, and compliance.

  • Primary Relational (Neon PostgreSQL): The source of truth for users, coupons, and rules. Serverless architecture scales to zero when idle and scales instantly under load. Point-in-Time Recovery (PITR) is enabled for 7 days.
  • Caching & Rate Limiting (Upstash Redis): Acts as a global cache.
    • cache:store:{slug} -> TTL 30 minutes. Caches the list of active coupons and bank offers to prevent hammering the DB.
    • rate:{ip}:{action} -> TTL based on limit.
  • Blob / Object Storage (AWS S3): Used exclusively for OCR image buffering. Configured with a private bucket policy, blocking all public access. The client gets a temporary pre-signed URL to PUT the object.

9. Development Workflow & CI/CD

We enforce a strict, automated pipeline to ensure high quality and zero-downtime deployments.

9.1 Branching & Environments

  • main -> Maps to Vercel Production and Neon Production DB.
  • develop -> Maps to Vercel Preview and Neon Staging DB.
  • feature/* -> E.g., feature/ocr-parser. Opening a PR automatically provisions a Vercel Preview URL and a dedicated Neon Database branch (cloned instantly via copy-on-write).

9.2 CI/CD Pipeline (GitHub Actions)

  1. Lint & Format: ESLint and Prettier check for code consistency.
  2. Type Check: tsc --noEmit ensures no TypeScript errors.
  3. Tests: Vitest runs unit tests on the Stacker Engine (critical to ensure pricing math is never broken).
  4. Deploy: If checks pass, Vercel Action deploys the code.

Key Risk Deep-Dives

Risk 9: RBI Regulatory Risk. Impact: High. Likelihood: Low. If we touch consumer funds or sell gift cards directly, we fall under RBI's Prepaid Payment Instrument (PPI) or Payment Aggregator (PA) guidelines. Mitigation: We act strictly as an aggregator and redirector. The user pays the marketplace (Amazon) or the affiliate partner (Gyftr) directly. We never touch the money.

Risk 4: ASCI Compliance. Impact: Medium. Likelihood: High. The ASCI has cracked down on undisclosed finfluencers and affiliate sites. Mitigation (AMD-04): Clear, non-dismissible UI badges indicating "Powered by Affiliate Commissions" are injected via Next.js layouts on all outbound links.

12. Future Roadmap

  • v1.0 (Current Scope): Web App, OCR parsing, 5-Layer Stacker Engine, Community Vault.
  • v2.0 (Q1 2027): Chrome/Brave Browser Extension. This will auto-apply the Stacker Engine directly on the Amazon/Flipkart checkout page. We also launch the internal "Coin Wallet" to allow users to withdraw their cashback portion via UPI.
  • v3.0 (Q3 2027): Machine Learning price drop prediction. Expansion to Southeast Asian markets (Shopee, Lazada). B2B API allowing smaller D2C brands to embed our card optimizer on their Shopify checkouts.

Scalability Plan

At 1k DAU, the current serverless Next.js + Neon setup handles load perfectly. At 10k DAU, we will implement Neon Read Replicas and shift more computation to the edge via Vercel Edge Functions. At 100k DAU, we will split the monolithic Next.js app, pulling the Stacker Engine into a dedicated Rust microservice behind a gRPC interface for maximum throughput.

15. Glossary

  • ASCI: Advertising Standards Council of India.
  • DAU: Daily Active Users.
  • GMV: Gross Merchandise Value (total value of goods sold through our links).
  • HMAC: Hash-based Message Authentication Code (used to secure URLs).
  • JSONB: A binary format for JSON data used in PostgreSQL for efficient querying.
  • LCP: Largest Contentful Paint (a Core Web Vital measuring loading performance).
  • OCR: Optical Character Recognition (used to read text from images).
  • ORM: Object-Relational Mapping (e.g., Drizzle, Prisma).
  • PA / PPI: Payment Aggregator / Prepaid Payment Instrument (RBI regulatory definitions).
  • PITR: Point-in-Time Recovery (database backup method).
  • RLS: Row-Level Security (PostgreSQL security feature).
  • SSR: Server-Side Rendering.
  • TTL: Time to Live (cache expiration time).
